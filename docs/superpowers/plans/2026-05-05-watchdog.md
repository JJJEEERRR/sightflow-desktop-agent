# Watchdog implementation plan (2026-05-05)

## Goal

Auto-restart the agent loop when it crashes, bounded by the existing
`RestartBudget` and exponential backoff. This is the missing recovery
loop on top of the Phase 1 `Lifecycle` FSM — Phase 1 explicitly deferred
it to keep that PR scoped.

## Module layout

```
src/core/runtime/
  watchdog.ts         (new)
  watchdog.test.ts    (new)
  index.ts            (re-export Watchdog + types)

src/core/engine.ts
  Add: when start() is called and lifecycle is in `recovering`, call
       `lifecycle.recovered()` after measureLayout succeeds. This is the
       handshake that lets Watchdog decouple itself from engine internals.

src/main/index.ts
  - Hold ONE Lifecycle across engine reconstructions (currently a fresh
    one is built on every engine:start).
  - On engine:start, build a `restartFn` closure that re-creates Engine
    using the latest config and starts it.
  - Build + start a Watchdog tied to the Lifecycle and the restartFn.
  - On engine:stop, stop the Watchdog first, then the Engine.
```

## Public API

```ts
export interface WatchdogClock {
  setTimeout(fn: () => void, ms: number): unknown
  clearTimeout(token: unknown): void
  setInterval(fn: () => void, ms: number): unknown
  clearInterval(token: unknown): void
  random(): number
}

export interface WatchdogOptions {
  lifecycle: Lifecycle
  /** Builds + starts a fresh Engine using the same shared Lifecycle.
   *  Resolves once `engine.start()` has been kicked off (does NOT await
   *  the loop). Rejects if construction or kickoff throws. */
  restart: () => Promise<void>

  baseDelayMs?: number // default 1_000
  maxDelayMs?: number // default 60_000
  jitterFraction?: number // default 0.2

  /** Optional liveness probe, called on `livenessIntervalMs`.
   *  Returning false `livenessFailureThreshold` times in a row → forces
   *  `lifecycle.crash(...)`. Throwing counts as a failure. */
  livenessCheck?: () => Promise<boolean>
  livenessIntervalMs?: number // default 30_000
  livenessFailureThreshold?: number // default 3

  clock?: WatchdogClock
}

export interface WatchdogStats {
  attempts: number
  lastDelayMs: number
  livenessFailures: number
  givenUp: boolean
}

export class Watchdog {
  start(): void // subscribes to lifecycle, no-op if already started
  stop(): void // unsubscribes, cancels pending recovery + liveness
  getStats(): WatchdogStats
}
```

## Recovery state machine

```
crashed
   │   (lifecycle event observed by Watchdog listener)
   ▼
schedule timer for backoff = clamp(maxDelay,
                                  baseDelay * 2^attempts) * jitter
   │
   ▼
lifecycle.recover()  ──false──▶ givenUp = true; log error; stop
   │ true
   ▼ (state is now 'recovering')
restartFn()  ──reject──▶ lifecycle.crash(err)  → loop again
   │ resolve
   ▼
(Engine itself transitions recovering → running via lifecycle.recovered())
```

## Why Engine drives `recovered()` (not Watchdog)

If Watchdog called `lifecycle.recovered()` immediately after `restartFn()`
resolved, we'd flip to `running` before the engine actually finished
`measureLayout`. By making Engine notice "I started from `recovering`"
and call `recovered()` after measureLayout succeeds, the lifecycle
accurately reflects the moment the agent is fully back online. If
measureLayout fails, the engine `crash()`-es on its own and the Watchdog
loop kicks in again — no double-counted attempts.

## Backoff formula

```
delay = min(maxDelayMs, baseDelayMs * 2 ** attempts)
       * (1 + (random() * 2 - 1) * jitterFraction)
```

attempts = `lifecycle.snapshot().restartBudget.used` at the moment of
scheduling (before `recover()` records the new attempt). So the first
crash waits ~1s, the second ~2s, the third ~4s, capped at 60s.

## Liveness check (designed, not enabled)

The API is included so Phase 4 can wire a per-tick heartbeat without
another API change. Today the only available signal is
`engine.isRunning()` which stays true through the entire loop and
therefore is not a useful liveness probe — wiring it would add noise
without catching real "stuck" cases.

`livenessCheck` is **not** registered by main in this PR. It is
exercised by unit tests against a fake clock to keep the contract
honest.

## Tests (watchdog.test.ts)

1. crash → recover happy path: backoff timer fires, lifecycle goes
   crashed → recovering → running (via fake restartFn calling recovered).
2. backoff doubles each attempt, capped at maxDelay.
3. jitter is bounded by ±jitterFraction.
4. budget exhaustion: after `max` failures recover() returns false,
   stats.givenUp = true, no further timers.
5. restartFn rejection re-crashes (lifecycle.crash from 'recovering').
6. stop() cancels pending recovery timer; no recover() is called.
7. liveness threshold reached → lifecycle.crash() with error reason
   "liveness".
8. liveness timer cleared when state leaves running.
9. start() is idempotent.

## Engine.test.ts additions

- start() called with lifecycle already in `recovering` does NOT throw
  and does NOT call `lifecycle.start()`; on success, calls
  `lifecycle.recovered()`.
- start() called from `recovering` with measureLayout failure still
  triggers `lifecycle.crash()`.

## Out of scope (deferred)

- Persisting the restart budget across electron app restarts (today the
  budget resets when main reloads — fine for now).
- Per-tick heartbeat instrumentation.
- Pause-on-error (rate limit / circuit breaker) — Phase 3 territory.
- Full process-level recovery (restart electron app) — Phase 4.
